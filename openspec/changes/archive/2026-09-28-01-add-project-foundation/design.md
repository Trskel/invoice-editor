# Design: project foundation

## Context

See proposal.md for motivation. Constraints found while preparing this change:

- `yarn install` requires Node 24.11 or later (`@babel/preset-env` engine range); `.tool-versions` pins Node 24.12.0 and yarn 1.22.22.
- `.prettierrc.json` sets `"parser": "typescript"` globally, so `prettier --check .` fails on images, `robots.txt` and `yarn.lock`, and would format Markdown or YAML as TypeScript.
- The tracked `.env` contains the placeholder `VITE_API_TOKEN=YOUR_API_TOKEN`; the real token lives in the ignored `.env.local`. Vite inlines `VITE_*` variables into the bundle at build time, so the token is public in any deployed build (inherent to a browser-only client; see NOTES.md).
- Deploy integrations and repository secrets are not available here, so deploying with the host's CLI is the simplest path.

## Goals / Non-Goals

**Goals:**

- One command runs every check, a failure points to one check, and each pull request shows the result for its head commit.
- Deployment is one command, reproducible from the repository, and safe against publishing a build without a token.

**Non-Goals:**

- Type-aware lint rules beyond the two promise rules below (slower, noisy on the provided infrastructure code).
- Accessibility lint (see Decision 1); accessibility is covered by role-based queries in tests and a manual pass before release.
- Removing unused starter dependencies or configuration.

## Decisions

### 1. ESLint 10 flat config with typescript-eslint and react-hooks

- `@eslint/js` recommended, `typescript-eslint` recommended, `eslint-plugin-react-hooks` recommended (rules of hooks, exhaustive dependencies, and the React Compiler-derived checks such as setting state during render).
- Two type-aware rules enabled on `src/`: `@typescript-eslint/no-floating-promises` and `@typescript-eslint/no-misused-promises`. Mutations and navigation return promises; an unhandled one hides errors.
- `--max-warnings 0` so warnings cannot pile up.
- The configuration file is `eslint.config.mjs`: the package has no `"type": "module"`, and the `.mjs` extension makes the file an ES module without changing how the other configuration files load.
- No `eslint-config-prettier`: neither ESLint 10 core nor the typescript-eslint recommended set contains formatting rules, so there is nothing to disable.
- Alternative considered: ESLint 9 to use `eslint-plugin-jsx-a11y`, whose latest release does not support ESLint 10. Rejected: pinning an older major version for one plugin; tests that query by role and accessible name catch the same class of issues on the pages we build.

### 2. Prettier covers the repository

- Remove the global `parser` so Prettier picks the parser from the file extension.
- `.prettierignore` adds `yarn.lock`, `public/`, `dist/`, `coverage/` and `.claude/` (generated by OpenSpec); `README.md` is removed from the ignore list since it becomes ours.
- `format` writes, `format:check` checks.

### 3. One `verify` script, result posted on the pull request

- `yarn verify` = `format:check`, `lint`, `typecheck`, `test --ci`, `build`, chained with `&&` (stops at the first failure; yarn prints the failing script). The order is cheapest first.
- `yarn verify:pr` (`scripts/verify-pr.mjs`) runs `yarn verify` and posts the output as a pull request comment with the GitHub CLI: head commit, Node and yarn versions, pass or fail, full output in a collapsed block. It refuses to run with uncommitted changes or when `HEAD` is not the pull request head, so the comment always describes the commit reviewers see. It posts failures too and exits with the `verify` exit code.
- Run it after the last push of a pull request; a new comment supersedes the previous one.
- Alternative considered: GitHub Actions (one job, five named steps, on pull requests and `main`). Rejected: CI is not enabled here, so the workflow only added a failed status to every pull request without running a check. The workflow is a small addition once Actions is available (NOTES.md).
- Alternative considered: pasting the output by hand. Rejected: easy to post output from a different commit or to skip the versions.

### 4. Cloudflare Pages, manual direct upload with a pinned wrangler

- `wrangler` as a pinned dev dependency (instead of a global install) so every deployment uses the same CLI version.
- Project creation (one time): `wrangler pages project create invoice-editor --production-branch main --force`. Wrangler 4.x now delegates new Pages projects to Cloudflare Workers; `--force` creates a classic Pages project, which keeps the `pages.dev` URLs, the preview branch alias and the single-page application fallback. Once the project exists, deployments run against Pages without the flag.
- `yarn deploy` = `node scripts/check-deploy-env.mjs && yarn build && wrangler pages deploy dist --project-name invoice-editor --branch main`.
- `yarn deploy:preview` = the same command with `--branch preview`. The project's production branch is `main`, so any other branch name creates a preview deployment, and Cloudflare keeps the stable alias `preview.invoice-editor.pages.dev` pointing to the latest one. The build is identical (production mode, same token check); only the URL differs. Preview URLs are public, like the production one.
- `scripts/check-deploy-env.mjs` loads variables with Vite's own `loadEnv` for the production mode, so it sees exactly what the build will see (`.env`, `.env.local`, process environment). It fails if `VITE_API_TOKEN` is empty or equals the placeholder `YOUR_API_TOKEN`, printing how to create `.env.local`. It never prints the value.
- Deep links: Cloudflare Pages serves `index.html` for unknown paths when the project has no top-level `404.html` (its single-page application mode). No `_redirects` file: a catch-all rewrite is redundant there and Cloudflare flags `/* /index.html 200` as a potential loop. Existing files (built assets) are always served as they are.
- Alternative considered: Workers static assets, the path Cloudflare now recommends for new projects (`wrangler.jsonc` with `not_found_handling: single-page-application`, previews through version aliases). Deferred: equivalent for this app, but it changes the URLs and the preview flow; listed in `NOTES.md`.
- Alternatives considered: Git integration or CI-driven deploys (need app installation or secrets); Netlify or Vercel (equivalent, but need an explicit rewrite rule and Cloudflare is the chosen host).
- Preview alternatives considered: a separate development environment (a second project or build mode) rejected because there is only one API instance, so it would add configuration without isolating data; a preview per branch name rejected because one fixed URL is enough for a single maintainer and easier to find; `vite preview` locally kept as a quick check, but it does not run the host's routing, which is what the preview verifies.

### 5. Starter code fixes, behavior unchanged

The new lint and format checks must pass on the existing code. Findings are fixed without behavior change (for example, adding the stable `api` reference to an effect dependency list, `@ts-ignore` to `@ts-expect-error` with a reason, formatting). Where the provided infrastructure needs an `any`, the line gets an inline disable comment with the reason. Pages that will be rewritten later are not refactored now.

### 6. Repository conventions for humans and AI

- `openspec init --tools claude`: `openspec/config.yaml` holds the project context and artifact rules; generated Claude Code commands and skills are committed so the workflow is reproducible.
- `CLAUDE.md` (short): stack, structure rules, commands, the spec-first workflow, and what must never be committed (tokens, `.env.local`).
- Pull request template: summary, linked issue, scenario-to-test table, verification (`yarn verify:pr` comment, preview URL checked), screenshots, trade-offs.

## Risks / Trade-offs

- [No server-side check: the result comes from the author's machine] → the comment records the commit and tool versions, the script refuses to run on anything but the pushed head, and anyone can reproduce it with `yarn verify` on that commit.
- [The token is visible in the deployed bundle] → inherent to a browser-only client with this API; documented in NOTES.md with the production alternative (a backend holding the credential).
- [Manual deployment can be forgotten] → deployment is a step in the pull request checklist, and the README shows the deployed version.
- [The preview shares the production API] → actions tested on the preview (create, finalize, delete) change real data; test with invoices created for the purpose, as with local development.
- [react-hooks recommended rules flag starter code] → fix without behavior change or suppress with a reason (Decision 5); anything larger is left to the pull request that rewrites that page.

## Migration Plan

1. Before merging, run `yarn deploy:preview` from the branch and smoke-test deep links on the preview URL.
2. Merge this change; run `yarn deploy` from `main`; smoke-test the production URL. Later pull requests follow the same order.
3. Rollback: Cloudflare Pages keeps previous deployments; promote the previous one from the dashboard or redeploy the previous commit.
